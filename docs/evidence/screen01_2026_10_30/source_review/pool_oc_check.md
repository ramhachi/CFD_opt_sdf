## Findings

### Q1 (P2) The P0 caches are not keyed, or not fully keyed, to the code: "re-validated under the reviewed fingerprint" is weaker than the text says
- Location: `scripts/screen01/screen01_pool.py:111-113` (`fingerprints`), `:123-131` and `:178` (`_load_cache("x1")` is called with `ok_fps=None`), `:148-151` (`stl_volume_file` reads `stl/<name>.stl` without checking it against the record's `stl_sha256`), `:160-173` (`parent_x1`: a cached record is returned unconditionally); `scripts/fid01/fid01_designs.py:32-47` (`DEPENDENCIES`/`fingerprint`); `scripts/screen01/screen01_freeze.py:36-41` (`REUSED`) and `:89`.
- Registration: §3.3 ("admissibility ... evaluated ... never re-decided"), §2 P0 and §10 (re-validated with the reviewed code fingerprint), adoption G18, README caveat ("cached rows are reused only under an identical `fid01_designs` dependency fingerprint").
- Facts: gate rows are keyed by `fid01_designs.fingerprint()`; the X1 records (78 files), the parent record and the STL files carry no key and no hash check. The fingerprint (and the freeze-1 `REUSED` list, which is `D.DEPENDENCIES` plus a few scripts) does not cover `fid01_designs.py` (the joint builder `raw_design` and `work`), `fid01_build.py` (`stl_volume`), `screen01_pool.py` (chain check), nor the gate-stack core: `src/cfd_sdf/design/geometry_gates.py` (`min_feature_width_m`, the binding R0 gate), `geometry_gates_v2.py`, `volume_semantics*.py`, `topology_policy_research.py`, `sdf_state.py`, `build_lowdim01_inputs.py`, `build_lowdim04a_inputs.py`, the topology-policy JSON and `v17_baseline.npz`.
- Scenario: nothing is wrong today (items 3 and 5 above). But after this review any fix that touches those files (including a defect found by the other two source reviews) leaves `D.fingerprint()` unchanged; `p0` then answers every member from the old gate rows and old X1 records, writes `d_fingerprint` equal to the old one, and `freeze1` (`:89`) passes: the record says "re-validated under the reviewed code" while no admissibility was recomputed. The same cache serves G2: a refinement point whose name is already cached (an unselected P0 member) would be answered from it without a check of the code that produced it, and the analyzer's `frozen_sources` hashes only the analyzer, checker and pool, not the gate stack.
- Fix: (a) add `fid01_designs.py`, `fid01_build.py`, `screen01_pool.py` and every `src/cfd_sdf/design/*.py` (plus `lowdim03_contract.py`, the policy JSON, `v17_baseline.npz`, `build_lowdim01_inputs.py`, `build_lowdim04a_inputs.py`, `xfid45_round3_export.py`, `step01_states.py`) to the fingerprint and to `REUSED`; (b) store the fingerprint in the X1 and parent records and filter `_load_cache("x1")` by it; (c) check `sha256(stl file) == rec["stl_sha256"]` before reading a volume; (d) if the code or the fingerprint changes, run `p0` from an empty `work/screen01_pool_prescreen/` (about 2.6 h at 4 workers) instead of from the cache. Without (a)-(c) the freeze text should say "cached rows were reused; fingerprint covers the files listed" rather than "re-validated".

### Q2 (P2) The headline P(GAIN) = 0.897 depends on the camber response continuing to rise to u = -1.5; the OC has no variant that tests this, although every GAIN finalist lies there
- Location: `scripts/screen01/screen01_oc.py:72-98` (`Truth.parts`: a per-mode quadratic fitted on u in [-1, 1] and evaluated to u = -1.5, plus a random cubic of SD 1e-3 N), `:262-275` (variants); registration §5.10 and §3.1, decision memo D2/D4.
- Registration item: §5.10 (the "Reading", "the camber extension adds 10.2 points and almost every GAIN finalist lies in it"), §1 claim ceiling (no FID fidelity evidence beyond 19.7 mm).
- Evidence: the fitted camber response is 1.30e-2 N at u = -1 and 2.06e-2 N at u = -1.5 (drag 2.1e-3 to 3.9e-3 N); `oc.json` has `P_finalist_in_extension = 1.0`. The variants `scaled_0.8/0.6` scale the whole downforce response (including the evidenced region), the misfit-heavy variant adds a cubic of SD 3e-3 N (a 1-sigma cubic is 1e-2 N at u = -1.5, but its sign is random, so it adds spread, not a systematic flattening). None flattens the response beyond the last evidenced amplitude. My rerun with the camber contribution held at its u = -1 value for u < -1 (both responses, otherwise identical, seed 20261031, 2000 replicates): P(GAIN) = 0.705 (NO_GAIN at selection 0.195), against 0.794 for the unextended box on the unmodified surrogate. FID already shows decreasing retention with camber amplitude (§3.1), so this is the case the registration itself flags as the expected one, but it is not quantified.
- Failure scenario: the registration (and the user's decision to fund about 18 GPU h) rests on "P(GAIN) 0.90 under the visible-data surrogate and at least 0.70 under every stress", where every stress keeps the extrapolated camber slope; if the physics saturates at -19.7 mm the procedure is a 0.70 procedure with 20 % `GAIN_BELOW_MIN_AT_SELECTION`. This changes no rule and no outcome mapping, only what the text promises.
- Fix: add the variant "camber response saturates at u = -1" (and, if wanted, "-1.25") to `main()` and to the §5.10 table and Reading (my value: 0.705), and state in the Reading that the 0.897 is conditional on the extrapolation; regenerate `oc.json`. No change to the procedure.

### Q3 (P3) The "null" row is vacuous and there is no power curve at the threshold
- Location: `screen01_oc.py:272` (`rev1_null_downforce`), `:101-103`; registration §5.10 ("the null truth never gives GAIN").
- With downforce noise SE 1.5e-4 N at P = 2 and x* = 7.18e-3 N (34 SE), a zero-downforce truth cannot pass the selection futility, so "never gives GAIN" (0.000, NO_GAIN at selection 1.000) is certain and says nothing about the selection-plus-confirmation rules. Revision 0's OC had rows with the best true gain at exactly g_min (the case the rule must handle: the point rule passes about 50 % there by construction, which is what XV_MARGIN_THIN then discloses); revision 1 dropped them. The relevant characteristic, P(GAIN) as a function of the finalist's true gain from 0.8 to 1.2 g_min, is not reported.
- Fix: replace or add a variant whose truth ceiling is 0.9-1.0 g_min (for instance `scale` about 0.37-0.41 of the extrapolated surface) and one threshold-power row; or reword the sentence to "the rule check with a null truth is trivial".

### Q5 (P3) Statements in the registration and memo that the record does not support, and one unreachable branch
- `§3.4`, `README`, `design_check.json`/`summary.json`: "random control: 48 sequence points for 19 admissible members". The control set is the first 19 admissible points in sequence order, which is reached at sequence point 36 (0-based index 35); 48 is the evaluation chunk (`RAND_CHUNK = 16`, `screen01_pool.py:239`), and `n_consumed` (`:246`, also in `freeze1`) records the chunk end. The 12 further points (6 admissible) are evaluated and unused. Record `n_consumed` = index of the 19th admissible + 1 (36) and keep the chunk end separately.
- `§3.6`: "R0 fails about 40-60 % ... (58 %, 45 %, 52 % of the random-control points)": 52 % is the admissible fraction of `rand3` (25/48); the failing fraction is 48 % (23/48).
- `decision_memo.md` D2: "the design pool spans the extension so the fit is not extrapolated". The design's lowest camber is u = -1.29 and the refinement optimum sits on the u = -1.5 face (and on reflex +1): the proposals are a 0.2 u extrapolation in camber (the quadratic is fitted, then evaluated there). State it as "mild extrapolation".
- `§3.3`/`§5.6` allow a `rand3` set of fewer than 19 (`K_MISMATCH`), but `screen01_build.py:90` and `screen01_freeze.py:90` refuse anything but 19; the K_MISMATCH-by-incomplete-control branch cannot occur (freeze fails closed, which is fine; say so).
- `§3.3` extension rule: extension is triggered only by "fewer than 12 admissible"; a pool with 12 or more admissible members but an inadmissible design (rank < 9 or cond > 20) at 64 points is neither extended nor covered by the terminal rule ("at 256 points"). Moot for the recorded P0 (cond 3.51); say that the design check follows the extension rule and does not trigger it.

### Q7 (P3) A gate-evaluation exception is cached as a permanent "inadmissible" without being counted
- Location: `scripts/fid01/fid01_designs.py:123` (`except Exception ... row["error"]`), `screen01_pool.py:116-145` (every returned row, error rows included, is written to `rows/<name>.json` and never retried), `:258-262` (`failed_gate_counts` counts only `failed_geom02`/`unmeasured_geom02`), `:212` (`r.get("all_pass")` is falsy for an error row).
- Failure scenario: a transient `MemoryError` or I/O error in one of 4 spawn workers (the P0 ran "under other load") turns a valid pool member, or a G2 refinement point, into "not admissible" for good: fail-closed as the text wants, but indistinguishable in `summary.json` from an R0 failure and not repeatable. P0 had none (0 error rows of 129).
- Fix: count `error` rows in the summary, refuse to cache them (or retry once), and make `freeze1`/the `rs` step fail on any gating row carrying `error`.
