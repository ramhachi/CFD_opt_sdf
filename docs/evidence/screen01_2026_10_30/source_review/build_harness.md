## Findings

### B1 - P1 - freeze 1 binds two files named `states.json`; the analyzer matches frozen files by basename and refuses at every stage
- Location: `scripts/screen01/analyze_screen01.py:527-530` (`check_frozen`: `hits = [... if Path(k).name == Path(path).name]`, `len(hits) == 1`), `:559-560` (`load_roles` -> `check_frozen(fz1, states_path, "states.json")`, called by `stage_input` for `rs`, `finalist` and `main`); `scripts/screen01/screen01_freeze.py:40` (`REUSED` contains `docs/evidence/unc01_2026_10_20/states.json`) and `:96` (freeze 1 binds `docs/evidence/screen01_2026_10_30/states.json`).
- Registration: §2 (each written-once step reads the verified tables and is checked against the freeze records), §9 (analyzer-defect protocol), §10 (freeze 1 content).
- Scenario: I wrote a `freeze1.json` with the real writer. Its `file_sha256` has two keys with basename `states.json` (the SCREEN one and the UNC-01 one) and two with `analysis.json` (FID and UNC-01). `analyze_screen01.check_frozen(rec, docs/evidence/screen01_2026_10_30/states.json)` raises `...: not the x frozen in screen01_freeze1`. So after G1 has run and verified, `analyze_screen01.py rs` fails in `stage_input` before it reads a force, and so do `finalist` and `main`. The analyzer is itself hash-bound by freeze 1 (`frozen_sources`), so the fix is an amendment of a frozen source after G1 forces exist (the blinding the registration builds around is then at stake). Nothing in the tests catches it: `tests/screen01/test_screen01_analyze.py` (`Disk`) builds a synthetic freeze 1 with a single `docs/evidence/x/states.json`, and `test_screen01_build.py::test_freeze1_content` never feeds the record to the analyzer. (`analysis.json` is also duplicated but is not looked up by name.)
- Fix (before freeze 1): look the file up by its repo-relative path, e.g. `rel = str(Path(path).resolve().relative_to(ROOT))` and `hits = [v for k, v in fz["file_sha256"].items() if k == rel]`; make the analyzer tests use real relative keys; add one cross-module test that runs `freeze1()` (as `test_freeze1_content` does) and passes its record to `frozen_sources` and `load_roles`. Same for the campaign lookups (they are unique today but share the mechanism).

### B2 - P2 - nothing checks which kernel the bound smoke table covers; the default `harness.py smoke` on the confirmation campaigns touches phase 13
- Location: `src/cfd_harness/campaign_build.py:182-184` (`smoke_kernel` default = min of `(solver_length, per_state_timeout_s)`, first in dict order), `:245-251` (`check_smoke_record`: one kernel of the campaign, no name); `scripts/screen01/screen01_freeze.py:71-80` (`campaign_record` only copies `smoke_verified_sha256`); `scripts/screen01/screen01_build.py:175-176`.
- Registration: §4.1 ("no confirmation phase is touched before freeze 3"), §4.2 (dedicated smoke-only kernels `f32smk`, `f48smk`).
- Scenario: the builder writes the campaign with sorted keys. For `screen01_f` the kernels are `f32a, f32b, f32smk` (all flow_32, per-state 900), for `screen01_f48` `f48k13, f48k14, f48smk` (all flow_48, 6,000). `scripts/harness.py smoke CAMPAIGN --source-commit X` without `--kernel` therefore renders and runs `f32a` / `f48k13`, whose first run is the parent at phase 13. `verify --smoke` and `harness.freeze` accept it (one kernel of the campaign), `freeze3` records the hash, and a confirmation-phase force of the parent has been produced and read before the frozen finalist runs. Only the module docstring of `screen01_build.py` says to pass `--kernel`.
- Fix: in `freeze2`, `freeze2_1` and `freeze3` open the smoke table (take its path as an argument or from `wl/smoke*/smoke_verify_table.json`), require `sha256 == freeze["smoke_verified_sha256"]` and `set(kernel_manifest_sha256) == {registered smoke kernel}` (`g1k11`, `g2`, `f32smk`, `f48smk`), and put the exact smoke command with `--kernel` into the registration/README.

### B3 - P2 - the registered per-state DATA_LOSS cannot arise on the harness; one bad state voids its kernel, and §5.1 / §9 / the signature table disagree about what happens
- Location: `src/cfd_harness/campaign_runner_template.py:277-280` (a state that exceeds its cap or does not complete raises; the kernel ends `ERROR`), `src/cfd_harness/campaign_verify.py:53,100,108` and `campaign_schema.py:353` (verify checks every state and raises on the first failure, including non-finite fields); registration §5.1 (DATA_LOSS list: non-finite force, cap exceeded, did not finish, verify failed), §9 ("a divergent run ... or a candidate the solver cannot handle is DATA_LOSS for that state-phase, never a reason to rerun" next to "or whose output fails harness verify" = INFRA_LOSS, one rerun), `docs/evidence/screen01_2026_10_30/infra_signatures.json` (`VERIFY_FAILED` is evaluated first and also matches every ERROR kernel, while `default_statement` says an ERROR kernel without a signature is not infrastructure and is never rerun).
- Scenario: one of the 39 states of g1k11 (a camber -29.55 mm joint point, an R state) diverges or exceeds 900 s. The runner stops, no table can be produced for the kernel, and all 39 runs of that phase are unusable. Whether it is then rerun once (INFRA_LOSS / `VERIFY_FAILED`, 4.6 h, deterministic, same failure) or declared lost at once (the default statement) depends on how the operator reads the three texts; either way `search_complete` becomes false (§5.9 row 1) and a would-be `NO_GAIN` becomes `INCOMPLETE`. The state-level `ok=false` / `null` branches of the analyzer and checker are reachable only with synthetic tables; only the 25 % implausibility bound is a real per-state loss. A non-search state (R, M, ref, NC) can cost the search phase.
- Fix (text, before freeze 1): say in §5.1 and §9 that per-state loss exists only for the implausibility bound and that any divergent, non-finite, capped or crashed state voids its kernel, which is classified `VERIFY_FAILED`, rerun once, then declared lost; delete the contrary sentence and align `default_statement`. No code change is needed. A runner that continues after a failed state would be a harness change and is out of reach now.

### B4 - P2 - the G1 aggregate cap is 1.2x the worst measured session; a trip at the tail of the kernel voids all 38-39 runs
- Location: `scripts/screen01/screen01_build.py:39` (`"g1": (900, 20000, 23300)`), registration §4.2 table row 1; runner `campaign_runner_template.py:277-278`.
- Registration: §4.2, §4.3 ("one G1 rerun (4.6 h) fits inside the cap; two do not").
- Scenario: the worst measured flow_32 run is 431 s (FID k10 mean 428), so g1k11 needs about 39 x 431 = 16,800 s of solver time against a cap of 20,000 s (headroom 19 %). The other kernels carry 1.35-1.45x and FID's own rule for flow_48 was 1.3x (`fid01_build.py:136`). Session-to-session spread is already 7.5 % between flow_32 session means (398-428) and 10 % between flow_48 session means (2,214 vs 2,428, FID vs UNC; 16 % over single runs, 2,178-2,516). A session about 19 % slower than the slowest flow_32 run seen (mean above 513 s per run) trips the cap at the last states (the random-control tail, the repeat); the runner raises after the state, the kernel is ERROR, verify fails, the whole phase is lost, and a second slow session loses it for good (the budget has room for one rerun only). The f48 kernels have 9,200 vs 3 x 2,516 = 7,548 s (1.22x), the same shape of risk for 3 runs.
- Fix: raise the g1 cap and timeout to the 1.3-1.45x used elsewhere (for example 26,000 / 29,300 s: still 8.1 h, under 12 h; the budget rule still uses the estimates) and, if wanted, the f48 cap to 10,500 / 13,800. This edits registered numbers (§4.2), so it belongs before freeze 1, not in a later engineering amendment.

### B5 - P2 - freeze 1 does not bind four data files the gate stack reads; the handoff cannot carry the policy hash §11 asks for
- Location: `scripts/screen01/screen01_freeze.py:36-41` (`REUSED`), `:143-149` (`handoff_skeleton`: `gate_profile_sha256` only), `scripts/screen01/analyze_screen01.py:702` (`gate_profile_and_policy_sha256` filters freeze 1 keys containing `gate_profile` or `policy`).
- Registration: §10 (reused code and inputs), §11 ("the gate profile and policy hashes").
- Scenario: an audit hook around `fid01_designs.work` shows the gate stack opens `docs/evidence/geom02_v17_gates_2026_10_14/geom02_resolved_research_policy.json`, `docs/evidence/p22_v17_volume_semantics_bridge_2026_10_11/inputs/v17_baseline.npz` (the 10 % smoothed-volume band baseline), `docs/evidence/opt01a_stage_a_2026_10_15/inputs/opt01_v1_parent.npz`, `docs/evidence/v18_genesis_2026_10_19/genesis.json`, besides the profile and the v18 parent npz that are bound. A `SCREEN01_GAIN` handoff therefore lacks the policy hash, and a change to one of these inputs between freeze 1 and the `rs` gating of the refinement points would pass silently (git content at the frozen commit is the only protection).

### B6 - P2 - the freeze writer is fail-open on untracked files and on harness-tool drift
