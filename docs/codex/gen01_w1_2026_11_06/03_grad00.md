# WP3：GRAD-00 の実装（対流スキーム λ の交換で forward AD の tangent が有界になるかを測る kernel と analyzer）

最初に `docs/codex/gen01_w1_2026_11_06/00_README.md` を読み、その規則に従うこと。仕様は `docs/grad00_lambda_swap_spec_2026_11_01.md`（GRAD-00、draft rev 0）。

## 目的

WaterLily issue #358 の報告（QUICK の内側の bound `10c−9u` を外すか、cds／vanLeer にすると ForwardDiff と中心差分が一致する）を、本リポジトリの登録済み測定（v17、flow_24、FD-08 の 4 方向、窓 [80,120]）で試す。凍結済みの GRAD-TA1 スクリプトを **コピーして** λ の腕を足し、各腕で plain primal・Dual run・±ε の primal 2 本を回す kernel と、FD-08 との比較・ラベル付けをする analyzer を作る。**Kaggle への push と GPU 実行はしない**（CPU のドライランまで）。

## 成果物

1. `scripts/quick_nobound.jl`：`quick_nobound(u,c,d) = median((5c+2d−u)/6, c, d)`（#358 のとおり。`quick_tie.jl` と同じく `Base.include(WaterLily, path)` で WaterLily の `median` を使う）。Float32／Float64／Dual のすべてで同じ式（分岐の追加なし）。
2. `scripts/waterlily_grad00_lambda_2026_11.jl`：GRAD-TA1 のコピー。変更は次に限る：
   - 腕の指定を環境変数 `GRAD00_ARM ∈ {quick, quick_nobound, cds, vanLeer}` で受け、`λ` を `WaterLily.Simulation(...; λ=λ)` に渡す（TA1 の Amendment 2 と同じ routing。`typeof(sim.flow.λ)` の検査も同じ）。
   - 各方向で、plain primal（その λ）、Dual run（tangent）、±ε の primal 2 本（ε は FD-08 の plateau の値を方向ごとに引数で受ける）を回し、`g2_run_index.json` に加えて `grad00_index.json`（腕、λ の型文字列、方向、plain／Dual／±ε の各 run の窓平均と SHA、watchdog の最大 tangent と onset、wall、VRAM）を書く。
   - 20-step の CPU preflight は TA1 と同じ（primal の有限性と tangent の有限性。quick 腕では primal が TA1 の `quick` 腕と bit-equal であることも確認）。
   - 精度の腕（仕様 F）：`GRAD00_T=Float64` で CPU 実行できるようにする（GPU では走らせない）。
   - それ以外（窓、サンプリング、BLOCKED の閾値、watchdog、エラーの伝播、index の名前）は **一切変えない**。コピー元との差分を `scripts/waterlily_grad00_lambda_2026_11.diff` として添える。
3. `julia/CFDSDFWaterLily110/`：WaterLily 1.10.0 を pin した **別の** Julia project（`Project.toml`、`Manifest.toml`）。本リポジトリの `src/` を `include` で共有する（`CFDSDFWaterLily.jl` を `Base.include` するか、`develop` で相対パス参照）。1.10 で変わった API（`Flow` の `uλ` → `u0`、Poisson の既定 tol、`mom_project!`）に job が触れるなら、その差を設計メモに書く。側腕 E はこの project で `GRAD00_ARM=quick` を回す。
4. kernel のレンダリング：`scripts/build_grad00_kernels.py`（既存のビルド経路を再利用）で、腕ごとに 1 kernel（`infra/kaggle/kernel_grad00_<arm>/`：runner.py、kernel-metadata.json、timeout）を **ローカルに生成するだけ**（push しない）。runner は pinned commit を clone する既存の方式。timeout は TA1 の実績（1 腕 ≈ 13 run の flow_24 ≈ 1 時間以内）＋余裕。
5. `scripts/analyze_grad00.py`：`docs/evidence/grad00_lambda_2026_11/<arm>/` の出力から、方向ごとに `BOUNDED`／`BLOCKED`、`AGREE`（符号一致かつ |tangent/FD − 1| ≤ 0.1、fx と fz の両方）／`DISAGREE`／`NOT_EVALUABLE`（|FD| < 3 × plateau の spread）、腕ごとに `BOUNDED_ALL`／`PARTIAL`／`BLOCKED_ALL`、plain primal の腕 A との差、精度腕の Float32／Float64 の差、仕様 §5 の「次の段の規則」の判定（≥ 1 腕が `BOUNDED_ALL` かつ `AGREE` ≥ 3/4 → `GRAD01_DRAFT_ALLOWED`）を `analysis.json` に **1 回だけ**書く（存在すれば拒否）。
6. テスト：`tests/test_grad00.py`（analyzer の全ラベルを合成データで、書き込み拒否、index の必須キー）、`scripts/grad00_selftest.jl`（`quick_nobound` の値が QUICK と一致する点と異なる点、Dual での partials の有限性、`cds`／`vanLeer` の存在確認）、CPU ドライラン（`G2_BACKEND=cpu G2_DRYRUN_T_END=…` で各腕の preflight が通る。実行時間は数分以内の設定で）。

## 受け入れ条件

- 4 腕すべての CPU preflight が通り、quick 腕の primal が TA1 の quick 腕と bit-equal（TA1 の preflight 出力と比較）。
- 1.10 の project が instantiate でき、同じ job が CPU preflight を通る（通らなければ、API 差を報告して `PARTIAL`）。
- `pytest -q tests/test_grad00.py` が通り、全体の失敗集合が base と同一。
- 報告に、各腕の予想 GPU 時間（TA1 の実績から）と、Kaggle へ push するための手順（ユーザー向け）を書く。

## やらないこと

- Kaggle への push、GPU 実行、TA1／quick_tie／DIAG のスクリプトの編集、Manifest の変更、閾値の変更（0.1、3×、1e30 は仕様の値）。
